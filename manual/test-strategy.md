# Стратегия тестирования Reservation Lab

Цель — проверить резервирование и согласованность остатков. Главные риски: лишнее списание, превышение остатка и двойной возврат. API-проверки покрывают варианты данных, UI — основные пользовательские сценарии, SQL — инвариант сохранения запаса.

| Приоритет | Область | Причина |
|---|---|---|
| P0 | Создание, недостаточный остаток, повтор, отмена, конкуренция | Нарушение количественного учёта |
| P1 | Невалидные данные, контракт, неизвестные сущности | Некорректные записи и ошибки |
| P1 | Сообщения UI, повтор после ошибки сети | Понятный результат операции |
| P2 | Визуальная проверка, клавиатура, адаптивность | Удобство и доступность |

## Окружение и данные

Python 3.11/3.12, Flask, SQLite, Chromium. Каждый тест — чистая база и отдельный порт. Нет зависимости от порядка тестов или доступности внешних сайтов. Email-адреса вымышленные. Источник ожидаемого результата — [требования](requirements.md).

## Критерии завершения учебного прогона

Все автоматизированные проверки прошли; в отчёте указаны команда, версии, результаты и ограничения. Ошибки дают ненулевой код завершения. На CI сохраняются JUnit XML и браузерные доказательства при падении. Зелёный локальный прогон не следует подписывать как зелёный CI.

## Исследовательские сессии

Результаты этих сессий **не заявлены как выполненные**: клавиатура; ширины 360/768/1440; потеря ответа после успешного сохранения; две вкладки; границы длины email и ключа; неизвестные JSON-поля; перезапуск сервера; превышение лимита тела запроса.

Для реального продукта отдельно нужны права доступа, изоляция клиентов, журналирование, секреты, rate limit, миграции, PostgreSQL, несколько экземпляров сервиса и мониторинг. Локальный стенд эти задачи не решает.
